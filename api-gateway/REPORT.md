# Звіт з навантажувального тестування та аналізу інфраструктури

## 1. Архітектура інфраструктури

Проєкт реалізовано на базі контейнеризації Docker (docker-compose) із суворим дотриманням принципів мережевої ізоляції.

- Odoo 19 (ERP) та PostgreSQL 15 знаходяться у внутрішній мережі (internal_network) і не мають жодних відкритих портів назовні.
- Next.js (API Gateway) виступає єдиною точкою входу, проксіюючи запити до ізольованої Odoo через протокол JSON-RPC від імені єдиного сервісного користувача.
- Безпека реалізована через Middleware у Next.js, який перевіряє x-api-key, валідує рівні доступу та веде логування запитів у JSON-файл. Налаштовано OpenAPI документацію.

## 2. Результати стрес-тестування

Тестування проводилося за допомогою утиліти autocannon на ендпоінт `GET /api/products`

npx autocannon -c 100 -d 10 -H "x-api-key: admin_key_999" http://localhost:3000/api/products


(імітація 100 одночасних підключень протягом 10 секунд).

- Загальна кількість оброблених запитів: 1725
- Успішність (HTTP 200): 100% (жодних відмов системи або помилок 5xx).
- Мінімальний час відповіді: ~34 ms
- Максимальний час відповіді: >10 190 ms (понад 10 секунд).

## 3. Аналіз "вузьких місць"

Система успішно витримала стрес-тест без падінь, однак логування виявило серйозну деградацію швидкості при високій конкурентності.

**Причина вузького місця:**

Асинхронний Node.js (Next.js) здатен приймати тисячі з'єднань миттєво. Проте Odoo, написана на Python, за замовчуванням обробляє запити синхронно (або з обмеженим пулом потоків). Під час генерації 100 одночасних запитів, Next.js миттєво передає їх по JSON-RPC до Odoo. Odoo не встигає опрацьовувати їх паралельно, через що утворюється черга. Саме тому перші запити обробляються за мілісекунди, а останні чекають у черзі по 8-10 секунд, перш ніж ERP-система зможе віддати дані з PostgreSQL.

## 4. Шляхи оптимізації та масштабування

Щоб вирішити проблему деградації швидкості при масштабуванні, пропонуються наступні кроки:

- **Впровадження кешування (Redis):** Для ідемпотентних запитів (наприклад, `GET /api/products`) необхідно додати Redis-кеш на рівні Next.js. Це зніме 90% навантаження з Odoo, оскільки API Gateway віддаватиме список товарів з пам'яті за 5-10 мс.
- **Масштабування Odoo:** Налаштування параметра `workers` у конфігурації Odoo для впровадження багатозадачності для паралельної обробки запитів, або підняття кількох реплік контейнера Odoo.
- **Rate Limiting:** Додавання лімітів на кількість запитів за секунду для конкретного `x-api-key` у Middleware, щоб один клієнт не міг монополізувати всі ресурси бази даних.
